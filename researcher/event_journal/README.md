# Event journal

This directory contains the public contract and recovery material for
SPEC-004. Runtime databases, WAL files, backups, receipts, and later shadow
outboxes live under ignored `researcher/runtime/event-journal/`; they are not
portable artifacts and must never be committed.

## Implemented slice

The current slice provides:

- registered `OrganizationEvent@1.0.0` and
  `ResearchRunTransition@1.0.0` contracts with Python/TypeScript parity;
- an exact-byte-pinned SQLite migration;
- canonical event BLOBs, optimistic subject versions, channel-scoped
  idempotency, and a journal-global SHA-256 chain;
- a deterministic research-run projector with subject-local quarantine;
- consistent online backup and receipt-bound restore through atomic private
  generation directories; and
- deterministic conformance evidence generated by
  `validate_event_journal.py`.

This is a research-run-only local prototype, not the accepted generic SPEC-004
journal. It has no trusted-principal/native/import authorization, registered
event-family dispatch, batch/bootstrap or recovery-ticket implementation.
The journal is not authoritative for `run-state.json`. File-first pending-ticket
mirroring and shadow comparison are later gated work; they do not themselves
authorize a cutover from repository files.

## Durability model

The store requires SQLite 3.37 or newer, a local filesystem, WAL mode,
`synchronous=FULL`, foreign keys, STRICT tables, and one connection per
operation. `append` acquires `BEGIN IMMEDIATE`, verifies the exact schema and
bounded journal/subject tails, resolves exact duplicates before checking the
current subject version, and commits the entry, subject version, and chain
head together. Full historical verification runs on open, explicit audit,
reads, replay, and backup rather than under every writer lock.

The hash chain is tamper-evident, not authenticated. A privileged operator who
can rewrite the database and every digest can forge a new chain. External
anchoring belongs to a later attestation specification.

## Recovery runbook

1. Stop writers. Preserve the database, `-wal`, and `-shm` files together.
2. Run `python researcher/scripts/validate_event_journal.py --check` to prove
   the public implementation and generated evidence are current.
3. Call `EventStore.verify_integrity()` on the affected runtime database.
   `JOURNAL_CORRUPT` is a global halt; do not continue appending.
4. For isolated inspection only, select a receipt-bound backup generation containing exactly
   `journal.sqlite3` and `receipt.json`. `restore_verified` verifies exact
   bytes, the complete event chain, schema contracts, subject indexes, and the
   logical tail before publishing a fresh local generation directory. This
   verifies the backup itself, not continuity with the latest accepted source
   tail. The prototype currently returns a writable store even for an older
   prefix; do not treat it as an authorized live replacement.
5. Rebuild the research-run projection and compare its digest with the prior
   checkpoint. A projection-only subject quarantine does not authorize editing
   event bytes.
6. Do not change a live runtime pointer or clear an operator halt through this
   prototype. `clear_operator_halt()` lacks the accepted recovery-ticket and
   known-tail continuity protocol. Retain the failed generation, its sidecars
   and latch for diagnosis. Authorized continuous reopen, declared-loss
   disaster recovery and deployment-pointer change remain unimplemented
   SPEC-004/SPEC-025 release blockers.

Backup and restore roots are private (`0700`); generation members are `0600`.
Incomplete `.staging-*` directories are never restore inputs and may be
garbage-collected only after confirming no process owns them. Rollback of this
slice means disabling consumers and retaining the journal for inspection; it
does not replay projection state into legacy files.
