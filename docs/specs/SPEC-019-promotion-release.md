# SPEC-019: Pull-Request Quality Gate, Promotion, and Release

Status: draft
Revision: 1
Revises: none
Wave: 3
Classification: split
Owners: release attestor agent; human maintainer
Depends on: SPEC-006, SPEC-007, SPEC-008, SPEC-016, SPEC-017, SPEC-018

## Decision

A candidate becomes `proposal_eligible` only after sequential hard gates and a Pareto review. An agent may then open a draft PR. Evaluation observations remain bound to immutable candidate content. An independent release attestor proves that the complete current PR tree and head SHA equal the exact base tree with the frozen candidate change manifest applied, and that every affected surface has current gate evidence. It also proves a contiguous quality lineage from the current promoted organization root: an ordinary attestation requires the PR base tree to equal that root, while a candidate whose base already contains an unattested accepted merge requires a separately declared cumulative-reconciliation attestation over the complete promoted-root-to-target-tree delta. Generated files, workflows, dependency locks, file modes, links, submodules, deletions, metadata, and intervening accepted bytes receive no attestation exception. Successful current-head and lineage attestation yields `merge_ready`; only human merge promotes it. A post-merge promotion record describes what was accepted; private deployment status is tracked separately by SPEC-025.

## Context and current repository touchpoints

Current CI already requires platform compatibility, strict repository validation, strict skill health, benchmarks, and activation cases. Plugin manifests share a prepared version. This spec preserves those checks, adds candidate/evaluation binding, expands surface-specific gates, and makes release state event-driven.

## Goals

- Prevent stale or unrelated results from approving a changed PR.
- Apply distinct gates to sources, mechanisms, skills, harnesses, and organization changes.
- Make production identity and rollback unambiguous.
- Keep the human review packet concise while retaining full evidence.

## Non-goals

- Auto-merge, agent release publication, or bypassing required reviews.
- One global weighted score.
- Requiring the same expensive evaluation for a typo and a harness change.

## Invariants

1. Admissibility, locked-surface, schema, repository, and provenance gates are hard vetoes.
2. The targeted failure improves by a preregistered practical amount and hidden behavior meets its non-inferiority bound.
3. At least one important dimension improves; no critical dimension regresses.
4. Negative controls remain stable and uncertainty is reported.
5. Cost, latency, context, and complexity remain within caps or form an explicitly accepted Pareto trade.
6. New skills require a distinct activation surface and maintenance justification.
7. Any new commit invalidates attestation until relevant checks rerun.
8. Promotion occurs only on human merge.
9. Evaluation observations, pre-merge attestation, and post-merge promotion are distinct immutable records.
10. A `PromotionRecord` records accepted public state only and never contains or claims an active deployment commit.
11. Attestation covers the entire Git tree and complete exact-base diff by reconstructing the expected head from the exact base plus the frozen candidate change manifest; a reviewed subset cannot authorize unrelated or generated bytes in the PR.
12. The release attestor is independent of the candidate proposer, search controller, primary evaluator, and identities that wrote the current PR head, and receives no persuasive author rationale beyond the declared candidate and gate artifacts.
13. Base movement, merge-queue rewriting, generated-output drift, or any head-tree change expires attestation before merge.
14. Merge, squash, and rebase are distinct materialization methods. The selected method and expected merge tree are proven before attestation; an unexpected method or tree cannot inherit the result.
15. PR-only metadata is an explicit non-executable allowlist with an exact digest. A title, body, label, review, or check mutation follows its declared expiry rule; no metadata field may carry code, generated release bytes, or an authority claim outside the attested tree.
16. Whether metadata is executable is proven, not assumed. Attestation inventories every workflow, App, repository rule, check, dispatch hook, and external automation that consumes PR metadata. A field that can trigger a privileged effect is removed from proposer write authority or treated as an authenticated command input that expires attestation.
17. The accepted-public pointer and promoted-quality root are distinct. A verified human merge may advance accepted public state without advancing the promoted root, but no later ordinary PR attestation may silently import that quality-lineage gap.
18. Every promotion either extends the exact current promoted root with a contiguous attestation or carries one cumulative-reconciliation attestation whose impact and gate evidence cover every byte from that root through the target tree. Attesting only the latest PR diff cannot repair an earlier gap.

## Interfaces and data

`EvaluationObservation` is defined by SPEC-017 and binds the candidate content digest and epoch without assuming a PR.

`ChangeImpactManifest` binds the exact base commit and tree, head commit and tree, frozen candidate snapshot, every changed path and Git object kind, mode and deletion, editable or locked-surface decision, owning specification, classification, schema and migration impact, generated-file generator and input receipts, dependency and workflow impact, and required gate set. It deterministically reconstructs the expected complete head tree by applying the frozen change manifest to the exact base and compares that tree with Git. It fails on an unclassified path, unexplained generated byte, submodule change, symlink or mode mismatch, omitted diff entry, or any reconstructed-to-actual tree difference. A cumulative-reconciliation manifest additionally starts at the current promoted root, inventories the complete accepted first-parent interval through the target, and treats every intervening path and object change as in scope even when it predates the current PR.

`PromotionAttestation` is a public record created before merge. It includes candidate and parent IDs; lineage mode `contiguous|cumulative_reconciliation`; the public promoted-lineage anchor or parent promotion record; exact promoted-root, base, and head commits and tree digests; the complete accepted first-parent interval being covered; complete change-impact-manifest digest; deterministic proof that applying the frozen candidate change manifest to the exact base yields the complete head tree; and, for cumulative reconciliation, deterministic proof that the manifest and gates cover the complete promoted-root-to-head delta including every intervening accepted change. It also includes exact PR and head SHA; public PR-metadata-manifest digest and new-identity public metadata-safety-decision ID; selected merge method; expected merge tree; required-check conclusions and trusted issuers; new-identity public evaluation-decision and gate-projection IDs; practical-effect and non-inferiority decisions; critical-dimension status; provenance completeness; compatibility classification; cost and complexity deltas; attestor identity and independence receipt; creation and expiry; and policy version. `contiguous` is valid only when the PR base tree equals the current promoted root. `cumulative_reconciliation` is valid only when its frozen manifest and all required evaluations cover the whole lineage gap rather than merely relabeling the latest candidate. Method-specific proof covers ordinary merge, squash, or rebase rather than assuming they materialize the same commit graph. A separate private `AttestationEvidenceSeal` binds the raw evaluation observations, hidden epoch and tasks, and their digests. The public attestation contains no private observation, consumer-inventory, installation, ruleset, or private-seal identity or digest and no merged commit.

`PullRequestMetadataManifest` is wholly public and permits only bounded title, body, issue links, allowlisted labels, requested reviewers, review state, and public check references already visible on the PR. It contains no installation ID, private rule or configuration, executable attachment, generated release artifact, capability, deployment command, unverified external body, or private digest.

A private `MetadataConsumerInventorySeal` covers repository workflows at the attested tree, installed Apps, repository and ruleset configuration, check definitions, dispatch hooks, and known external automation and binds their exact private evidence. The release attestor derives a new-identity `PublicMetadataSafetyDecision` containing only the public PR identity, bounded allowlisted field set, safe/unsafe conclusion, expiry class, policy version, and public reason codes. It carries no private inventory identity, digest, installation/configuration value, or count. A field is ordinary non-executable metadata only when the private seal supports that public conclusion. Otherwise the proposer is denied write access to the field, or changes must enter through a SPEC-006 authenticated command family and expire attestation. The merge reconciler checks the current public manifest digest and public decision ID; private evidence remains in the seal and is never digest-linked from a public record.

A separate release-attestor GitHub App publishes the head-bound attestation check. It has `Checks: write` and the minimum metadata read needed to bind repository and head, but no contents write, pull-request write, branch, review, merge, ruleset, deployment, or proposer capability. Required-check policy pins its App installation identity, check name, conclusion vocabulary, and exact head SHA. The proposer App cannot create or update that check, and the attestor cannot change candidate bytes or PR metadata.

`PromotionRecord` is a deterministic public SPEC-019 projection derived only after a reconciled human merge. It includes the public attestation ID and digest, lineage mode, exact parent promoted-lineage anchor, promoted-root commit and tree, covered accepted interval, public PR and attested head SHA, merge commit and tree, accepted public commit, next organization version derived from the current SPEC-004 epoch, schema and public artifact inventory, compatibility scope, human merger, and rollback parent. Its parent must equal the current promoted root at projection time; a cumulative record is accepted only when the attestation closes the entire previously unpromoted interval. A private `PromotionProjectionReceipt` binds the immutable SPEC-007 repository-acceptance event, provider/ruleset/authority evidence, private epoch source, public output identity and digest, and projector version. The public record contains no source acceptance-event identity or digest, private observation or seal identity, private inventory digest, or equality oracle, and it does not claim that a private deployment is already active. It is not a second promotion event or a caller-authored journal mutation; deleting the projection store and replaying the same private sources yields identical public bytes and organization version.

Because a record containing a merge SHA cannot be inside the commit it describes, the immediate operational record is derived outside that tree from the immutable accepted-event and attestation sources and may be linked as an immutable-digest status or comment on the merged PR. A deterministic public promotion-ledger snapshot can be included in a later agent-opened maintenance PR. That later snapshot does not cause or retroactively authorize the original promotion.

After the one-time SPEC-004 baseline, SPEC-007 is the sole ongoing writer of `accepted_public_commit` from authoritative GitHub merge reconciliation. This specification consumes that merge fact and the current SPEC-004 organization epoch, and owns `PromotionAttestation`, the independent promoted-quality root, attested-quality classification, the pure organization-version projection, and `PromotionRecord` for a merge that matched a current attestation. An authorized human merge without attestation is still reflected by SPEC-007 as public acceptance but receives `unattested_acceptance`, no fabricated `PromotionRecord`, and no organization-version advance. The promoted root remains unchanged. A later ordinary attestation whose base includes that merge is denied; recovery requires a cumulative-reconciliation attestation over the complete last-promoted-tree-to-target-tree delta. No unresolved gap can satisfy SPEC-025 activation. This specification neither owns nor projects active deployment state. SPEC-025 later consumes a valid promotion projection and owns private activation; SPEC-008 may later combine independently sourced accepted and active pointers in status.

Public attestation and promotion records are new-identity allowlisted projections. Hidden evidence seals, deployment activations, raw check receipts, private evaluator identities, and installation-specific rollback state remain private and expose no private digest through the public projection.

Gate policy maps change surfaces to required stages. Skill prose requires Stages 0-3 plus routing delta when activation changes. Composition-sensitive changes require Stage 4. Context, workflow, recovery, or harness changes require Stage 5. Optimizer changes require Stage 6. A community question follows its own relevance, uncertainty, answerability, and human-publication gates.

## State and failure behavior

Candidate release state moves `proposal_eligible -> draft_pr_open -> attestation_requested -> merge_ready|attestation_denied|attestation_expired`. Attestation internally moves `requested -> promoted_root_verified -> base_and_head_verified -> full_tree_verified -> lineage_impact_closed -> merge_tree_verified -> inputs_verified -> gates_evaluated -> independently_attested|denied|expired`. PR state follows SPEC-007. A mismatch in candidate digest, promoted root, accepted interval, base, reconstructed head tree, complete diff, impact manifest, PR metadata, merge method or expected tree, epoch, independence, or required checks denies attestation. A new accepted pointer, promoted root, base, head SHA, tree, material metadata digest, merge method, or merge-queue result expires it. After SPEC-007 emits the one merge-derived accepted pointer, this specification's independent quality projection moves `merge_observed -> lineage_verified -> merged_tree_verified -> promotion_recorded -> attested_acceptance`; a merge without a current matching attestation becomes `unattested_acceptance` and an incident, without fabricating evaluation, promotion, or deployment approval. That state advances only the accepted pointer, not the promoted root.

## Implementation sequence

1. Generate change-impact manifests, the public bootstrap lineage anchor, and the independent accepted-pointer/promoted-root projection; map surfaces to gates.
2. Generate complete change-impact manifests, bind raw evaluation observations to candidate content in a private evidence seal, derive public evaluation-decision projections, and prove exact base/head/full-tree equivalence.
3. Implement independent exact-SHA attestation and current-check verification.
4. Deterministically project a separate promotion record and organization version after an observed accepted human merge; enforce compare-and-project against the exact current promoted root and prove clean rebuild parity.
5. Add accepted-public version and compatibility updates plus the accepted-configuration rollback runbook; deployment projections remain outside this specification.

## Migration and rollback

SPEC-004 creates the human-authorized accepted-public and organization epoch-zero baseline before SPEC-007 activation. This specification consumes that exact baseline and creates neither a fabricated attestation nor promotion for it. A current-state baseline audit may create a separately typed `BaselineAttestation`; it is not a `PromotionRecord` and cannot claim a historical pre-merge gate. Existing releases receive best-effort historical acceptance records under the same distinction. `PromotionRecord` remains reserved for a genuinely attested, subsequently observed human merge. Accepted-configuration rollback is a human-merged revert or corrective PR, never history rewriting. It appends events and verifies the resulting accepted pointer. SPEC-025 separately defines any operational rollback and deployment activation; this specification does not depend on that later state.

## Verification

- A commit after successful attestation invalidates attestation; unchanged evaluation observations remain attached only to their frozen candidate digest.
- A path, file-mode, symlink, submodule, generated output, workflow, lockfile, or deletion outside the reviewed candidate makes full-tree attestation fail.
- Base movement, material PR-metadata change, merge-method change, or a merge-queue tree different from the attested expected tree expires attestation and requires current-tree checks.
- A label consumed by a privileged workflow is rejected from the proposer allowlist or requires authenticated command authorization and attestation renewal.
- Public metadata artifacts expose no installed-App, ruleset, external-automation, or private consumer-inventory identity or digest; changing the private evidence produces a new public safety decision without identity linkage.
- Merge, squash, and rebase fixtures verify the exact resulting tree or deny; none reuses another method's proof.
- A candidate with aggregate gain but critical provenance regression is denied.
- A new skill without distinct activation evidence is denied.
- The proposer cannot act as sole attestor.
- The primary evaluator, search controller, and writer of the attested head cannot act as release attestor.
- Human merge produces one promotion record bound to the attested head and merge commit.
- An unattested accepted merge leaves the promoted root unchanged. A later ordinary attestation based on that unpromoted tree is denied, even when its own PR diff and gates pass.
- A cumulative-reconciliation fixture promotes only when its manifest, evaluation, and gates cover the complete last-promoted-tree-to-target-tree delta; omitted or reordered intervening commits, paths, generated bytes, or failure surfaces deny it.
- Concurrent or stale promotion projections cannot advance from the same parent promoted root twice; exact replay is byte-identical.
- Public promotion-ledger export avoids circular commit hashing and reproduces the immediate post-merge record.
- A PR SHA cannot appear in an evaluation observation, and a merged commit cannot appear in a pre-merge attestation.
- A rollback drill restores the prior accepted configuration through a human-merged PR.
- Replaying the immutable journal after rollback reproduces the accepted-public projection without deleting post-promotion events.

## Acceptance criteria

- [ ] Every `proposal_eligible` candidate may open only a draft PR; only a current exact-SHA independent attestation can produce `merge_ready`.
- [ ] Attestation closes the complete base-to-head impact and exact full PR tree with no generated-file or metadata exception.
- [ ] Current PR-only metadata and the selected merge method are digest-bound, allowlisted, and verified against the expected merge tree.
- [ ] Required gates depend on changed surfaces and are machine-checkable.
- [ ] Existing strict validators remain required.
- [ ] Human merge is the only promotion trigger.
- [ ] Accepted-public and promoted-quality pointers are distinct, and every promoted organization version proves a contiguous or cumulative fully gated lineage from the prior promoted root.
- [ ] Accepted public version and rollback pointer are independently queryable without claiming deployment state.
- [ ] Release and plugin manifest consistency is validated.
- [ ] Rollback is an event-appending, replay-verified transition rather than a history or database rewind.

## Pull-request evidence

Attach gate matrix, change-impact examples, candidate-to-tree proof, stale-SHA denial, critical-regression denial, accepted-but-unattested gap denial, cumulative-reconciliation pass and incomplete-interval denials, stale-parent promotion denial, separate sandbox observation, attestation, and promotion records, version-consistency result, rollback drill, and negative schema/projection proof that promotion neither claims nor triggers deployment. Deployment and activation evidence belongs only to SPEC-025.
