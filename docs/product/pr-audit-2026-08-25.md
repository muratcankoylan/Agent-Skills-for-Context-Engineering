## Branch-rule gate before #121

At assessment, the active default-branch ruleset required a pull request and
resolved threads, but had no required status check, zero approvals, all three
merge methods enabled, and an always-bypass administrator role. The repository
had one collaborator, who authored the train, so a one-approval requirement
would deadlock until a separate reviewer identity exists.

Minimum train-safe settings:

- require the exact `validate` check from GitHub Actions App integration `15368`
  with strict up-to-date heads;
- allow merge commits only; disable squash, rebase, and auto-merge;
- remove bypass actors from the quality ruleset;
- retain deletion, non-fast-forward, pull-request, and thread-resolution rules;
- keep required approval count at zero only as a documented single-owner train
  exception, with an authenticated exact-head human review recorded procedurally.

Before autonomous proposal operation, separate the human owner's GitHub identity
from automation. A dedicated GitHub App may propose and reconcile but must not
update `main`, merge, edit rules, or approve its own work. After that separation,
require one stale-dismissing, last-push, code-owner approval from the human.

## Production blockers surfaced by the backlog

The audit identified five defects that should be rebuilt as narrow changes on
the final train tip rather than merged from stale branches:

1. batch and item path containment in `pipeline_template.py`;
2. hosted-agent Git credential and shell handling;
3. the interleaved-thinking calculator's unrestricted evaluator;
4. Windows continuous-loop locking policy; and
5. mandatory pre-call reservation, retry accounting, and non-evidence dry-run
   semantics for paid examples.

The first three have small, locally testable correction surfaces. The last two
need explicit cross-platform and provider-budget contracts before code is
presented as production-safe.
